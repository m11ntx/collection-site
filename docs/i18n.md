# i18n — PT/EN language switch (CS-19)

A client-side dictionary + `localStorage`, no routing, no build step — consistent
with the site's "vanilla JS, no frameworks" constraint. Default language is
**EN**.

## The frozen hero is never translated

`index.html`'s hero/landing (`<div class="landing" id="top">`) is **hardcoded
English and carries no `data-i18n*` attributes at all** — it is not part of
the language switch. Reason: the nav (and its language toggle) is hidden over
the hero and only reveals itself once the user scrolls past it
(`UI.initNav()`), so there is no visible way to know or change the language
while looking at the hero. Translating content the visitor has no way to
switch back would be confusing, and the hero is separately frozen by design
(see the root `CLAUDE.md`) — so it stays exactly as originally shipped,
regardless of the active language. The site-wide default is **EN** specifically
so this always-English hero never looks mismatched against the rest of the
page. Every other page has the nav (and toggle) visible immediately —
`UI.initNav()`: "Subpages (no hero): keep the bar visible at all times" — so
they translate normally.

## Architecture

Everything lives in **`assets/js/i18n.js`** (loaded right after `config/site.js`,
before `catalog.js`/`ui.js` on every page). It exports `window.I18N` in the
browser and `module.exports` in Node (same UMD pattern as `filters.js`), so it's
directly testable and directly `require()`-able from `scripts/gen/gen_pages.js`.

- **`STRINGS = { pt: {...}, en: {...} }`** — every static UI string (nav,
  footer, hero, empty states, spec labels, the customer journey, FAQ,
  institutional page bodies), one dictionary, both languages side by side so a
  missing translation is obvious at a glance.
- **`FIELD_LABELS`** — display labels for the small set of already-controlled
  values in `data/products.json` (`type`, `category`, `gender`, `version`).
  The JSON values themselves never change (RN-012) — this only maps a value
  like `"Men"` to the label `"Masculina"` in PT. Unknown future values pass
  through unchanged (never throws, never blanks).
- **`PROPER_NOUNS`** — same idea for `collection.name`, `region.name`,
  `league.name` and `club.name` (`"Brasil"` → `"Brazil"`). Keyed by the raw
  JSON value; missing entries pass through unchanged — this is why real club
  names (Barcelona, Real Madrid, Flamengo) need no entry at all, while the
  Seleções league's national-team "clubs" (whose `name` is a PT country name,
  e.g. `"Alemanha"`) do (MI-36/CS-51). `catalog.js` calls
  `I18N.properNoun(...)` on every `club.name`/`league.name`/`region.name`/
  `collection.name` used in visible card/detail/breadcrumb markup.
- **`NAME_DICTIONARY`** — ordered, longest-phrase-first PT→EN word/phrase
  substitution for the free-text jersey `name` field (see below).
- **`t(path, vars)`** — dotted-key lookup into `STRINGS[lang]`, falls back to
  `pt` then to the literal path string. Supports `{var}` interpolation.
- **`getLang()` / `setLang(lang)`** — `localStorage["m11ntx_lang"]`. MI-03:
  switching no longer reloads the page — `setLang()` persists, re-runs
  `applyStatic()` + `initLangToggle()` in place, and fires a
  `"language:change"` DOM event (`detail: {lang, locale}`) so dynamically
  rendered content (product cards, jersey detail — anything built from a JS
  template rather than static `[data-i18n]` markup) can re-render itself
  from already-fetched data. `catalog.js` listens for this once and re-runs
  its last render call; the catalog itself is never re-fetched. The
  build-time `gen_pages.js` fallback still just reads `getLang()` fresh at
  generation time, unaffected by this.
- **`applyStatic(root)`** — walks the current DOM for three attributes and
  fills them from `t()`:
  - `data-i18n="path"` → `el.textContent`
  - `data-i18n-html="path"` → `el.innerHTML` (static trusted dictionary
    content only — never user input)
  - `data-i18n-attr="attr:path;attr2:path2"` → sets one or more attributes
    (used for `aria-label`, `placeholder`, `alt`)
  - `data-i18n-steps` / `data-i18n-faq` → filled via `renderStepsHtml()` /
    `renderFaqHtml()` (see below)
- **`initLangToggle()`** — wires every `.js-lang-toggle` button (desktop nav +
  mobile menu) and sets `document.documentElement.lang`/`data-lang`.

`main.js` calls `I18N.init()` (= `applyStatic()` + `initLangToggle()`) first,
before `SEO`/`Analytics`/`UI`/`Catalog`.

## Two content paths: static markup vs. `catalog.js` templates

- **Static shell** (nav, footer, hero, institutional prose, search overlay):
  tagged with `data-i18n*` attributes in the HTML, filled by `applyStatic()`
  once on load.
- **`catalog.js`-rendered content** (collection/club/jersey cards and detail
  pages): calls `I18N.t(...)` / `I18N.fieldLabel(...)` / `I18N.translateName(...)`
  **directly inside the template-building functions**, so the correct-language
  HTML is baked in at render time — no `data-i18n` attributes needed there, and
  no second translation pass after `innerHTML =`.

## One shared "How It Works" steps / FAQ list

Before this change, "How It Works" and "FAQ" content existed as **three or
four divergent copies** across `pages/how-it-works.html`, `pages/faq.html`, and
`catalog.js`'s embedded jersey-page journey section — different item counts,
different wording. `journey.steps` / `journey.faq` in `STRINGS` are now the
**single source**; `I18N.renderStepsHtml()` / `renderFaqHtml()` render them to
HTML and are used by both `catalog.js` (jersey page) and, at **build time**,
`scripts/gen/gen_pages.js` (which `require()`s `i18n.js` in Node — reading
`I18N.getLang()`'s default, so the fallback always tracks whatever
`DEFAULT_LANG` is — to generate the static fallback for
`pages/how-it-works.html` / `pages/faq.html` before `data-i18n-steps` /
`data-i18n-faq` take over client-side).

## `translateName()` — what it is and isn't

The jersey `name` field is free text from the source (e.g. `"Camisa Retrô
Barcelona Home 10/11 Torcedor Nike Masculina - Azul e Vermelho"`). There is no
translation API in this static, no-backend site, so `translateName()` is
**rule-based phrase/word substitution**, not machine translation: it walks an
ordered dictionary (longest phrases first — `"Azul Marinho"` before lone
`"Azul"`) and swaps known PT vocabulary for English, preserving the original
word's capitalization. It is grammatically approximate (word order stays PT)
but covers 100% of the vocabulary in today's `data/products.json`, verified by
`tests/i18n.test.js` against every real product name.

**Why not `\bword\b` regexes:** JS's `\b` treats accented characters (`ô`, `ã`,
`é`…) as non-word characters, so `\bRetrô\b` silently fails to match at the
boundary right after `ô`. `phraseRegex()` uses lookaround on
whitespace/comma/hyphen/string-edges instead, which sidesteps that.

**To add new vocabulary** (e.g. a new color or a recurring phrase): add an
entry to `NAME_DICTIONARY` in `assets/js/i18n.js` — phrases before the single
words they contain — and add a case to `tests/i18n.test.js`'s "leftover PT
tokens" list if it's a common word.

**Club/league/collection/region proper nouns are not translated** by
`translateName` (it only runs on the jersey `name` field) — they're either
already language-neutral (real club names: Barcelona, Real Madrid) or go
through `PROPER_NOUNS` instead (collection names: Brasil → Brazil; the
Seleções league itself and its national-team "clubs": Alemanha → Germany).

**Verifying there's no leftover PT vocabulary**: `tests/i18n.test.js`'s
"no unexpected leftover accented tokens in en" test runs `translateName()`
against every real product name in `data/products.json` and fails if any
non-allowlisted word with an accented character survives — a broader,
self-updating check than hand-picking a handful of known words. When it
fails on a genuinely new proper noun (a new club/place/person name), add
that word to the test's `allowlist`; when it fails on real vocabulary,
add the word to `NAME_DICTIONARY` instead.

## Explicit exclusions (by design, not oversight)

- **`filters.js` / `search.js` facet labels & placeholders** — not mounted on
  any shipped page yet (no `Filters.mount`/`Filters.attach` call sites outside
  their own files/docs). Translate when the catalog page ships.
- **SEO `<head>` meta/OG/Twitter/JSON-LD`** (`seo.js`) — no server-side
  language negotiation exists on static GitHub Pages, so crawlers never see
  the client-side toggle. Only visible body content + `documentElement.lang`
  switch client-side; `<head>` tags stay at their static per-page default.
- **`catalog-pipeline` / the canonical data model** — untouched. i18n is a
  pure display layer in `collection-site`; `data/*.json` values are identical
  regardless of which language is showing.

## Size labels (`SIZE_LABELS`)

Brazilian size letters (`data/*.json`'s `sizes[].size`) map to the
equivalent EN scheme for display — the underlying stored value never
changes, same pattern as `FIELD_LABELS`:

| PT | EN |
|----|----|
| PP | XS |
| P  | S  |
| M  | M  |
| G  | L  |
| GG / XG | XL |
| 2GG | 2XL |
| 3GG | 3XL |
| 4GG | 4XL |

`XG` is treated as a synonym of `GG` (both mean "extra grande" in real Feng
listings). `I18N.sizeLabel(size)` is case-insensitive and falls through
unchanged for anything it doesn't recognize (e.g. a mis-mapped customization
option that ended up in the `size` field by a source/normalizer quirk) —
never blank, never throws. Used in `catalog.js`'s jersey-page size chips.

## Adding a new UI string

1. Add the key to **both** `STRINGS.pt.<path>` and `STRINGS.en.<path>` in
   `assets/js/i18n.js` (the `i18n.test.js` key-parity test fails loudly if one
   language is missing a key).
2. Reference it with `data-i18n="<path>"` in static HTML, or `I18N.t("<path>")`
   inside a `catalog.js` template function.
3. If it's on an institutional page generated by `scripts/gen/gen_pages.js`,
   re-run `node scripts/gen/gen_pages.js` after editing `STRINGS`.
4. Run `node scripts/gen/minify.js` after editing any JS/CSS.
5. `node tests/i18n.test.js` (plus `filters.test.js` / `search.test.js`) to
   confirm nothing broke.
